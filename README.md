# Продуктовая аналитика e-commerce на SQL: активность, воронка, когорты

Серия аналитических SQL-запросов (PostgreSQL) поверх сырых логов пользовательских
событий интернет-магазина: от базовых метрик вовлечённости до когортного анализа
удержания.

| Вопрос бизнеса | Метрика | Блок |
|---|---|---|

## Данные

[eCommerce events history](https://www.kaggle.com/datasets/mkechinov/ecommerce-events-history-in-electronics-store) - логи реального интернет-магазина электроники.
Одна строка = одно событие пользователя с товаром.

```sql
CREATE TABLE events (
    event_time      TIMESTAMPTZ,    -- время события (UTC)
    event_type      VARCHAR(20),    -- 'view' | 'cart' | 'remove_from_cart' | 'purchase'
    product_id      BIGINT,
    category_id     BIGINT,
    category_code   VARCHAR(200),
    brand           VARCHAR(100),
    price           NUMERIC(10, 2),
    user_id         BIGINT,
    user_session    UUID            -- идентификатор визита, ключ для воронки
);
```

## Стек

- **Оконные функции** - `ROW_NUMBER`, `LAG`, `FIRST_VALUE`, `SUM/AVG OVER`, скользящие рамки (`ROWS BETWEEN`)
- **CTE** - многоуровневые цепочки `WITH` для читаемости сложной логики
- **Агрегатные функции с `FILTER`**, `PERCENTILE_CONT`, `CASE WHEN`
- **Работа с датами** - `DATE_TRUNC`, `EXTRACT`, интервальная арифметика
- **Docker Compose** - воспроизводимое окружение
- **Python** - генератор синтетических данных для проверки запросов

## Блок 1 — Метрики активности

**Файл:** [`sql/02_activity_metrics.sql`](sql/02_activity_metrics.sql)

| Запрос | Что считает |
|---|---|
| 1.1 | DAU + скользящее среднее за 7 дней + разбивка «будни / выходные» |
| 1.2 | WAU по ISO-неделям + прирост неделя к неделе |
| 1.3 | MAU, Sticky Factor, сессий на пользователя, динамика MoM |

**Sticky Factor** = средний DAU за месяц / MAU этого месяца. Отвечает на вопрос
«какую долю месячной аудитории продукт удерживает в среднем в каждый отдельный
день». Ориентиры для интерпретации: выше 20% — сильная вовлечённость, 10–20% —
норма для e-commerce с редким циклом покупки, ниже 10% — продукт используют
эпизодически.

> **Методологическая деталь.** MAU не равен сумме DAU за месяц: пользователь,
> заходивший 10 дней подряд, даст 10 в сумму DAU, но только 1 в MAU. Поэтому
> каждый уровень агрегации считается отдельным `COUNT(DISTINCT user_id)`,
> а не суммированием уровня ниже.

## Блок 2 — Анализ воронки

**Файл:** [`sql/03_funnel_analysis.sql`](sql/03_funnel_analysis.sql)

| Запрос | Что считает |
|---|---|
| 2.1 | Воронка View → Cart → Purchase: micro- и macro-конверсия, точки потерь |
| 2.2 | Динамика конверсии по месяцам |
| 2.3 | Скорость прохождения шагов (медиана и p90 времени между шагами) |
| 2.4 | Анализ брошенных корзин |

Три решения, определяющие корректность расчёта:

1. **Единица анализа — сессия, а не пользователь.** Воронка описывает поведение
   внутри одного визита. Если считать по пользователям, конверсия завышается:
   просмотр в январе и покупка в марте — это не прохождение воронки.

2. **Шаги засчитываются только в хронологическом порядке.** Наивная проверка
   «в сессии есть view И есть cart» засчитает визит, где пользователь пришёл по
   прямой ссылке в корзину и лишь потом открыл карточку товара. В запросах каждый
   следующий шаг ищется строго после времени предыдущего — через `ROW_NUMBER()`
   в подзапросе, выбирающем первое подходящее событие.

3. **Воронка монотонна по построению.** Шаг 3 джойнится к шагу 2, а не к шагу 1,
   поэтому каждое следующее множество сессий — строгое подмножество предыдущего.

Micro- и macro-конверсия считаются оконными функциями (`LAG` и `FIRST_VALUE`)
поверх «длинного» представления воронки, а не ручным делением колонок.

## Блок 3 — Когортный анализ

**Файл:** [`sql/04_cohort_retention.sql`](sql/04_cohort_retention.sql)

| Запрос | Что считает |
|---|---|
| 3.1 | Retention Rate в % — сводная таблица (когорты × месяцы жизни) |
| 3.2 | То же в абсолютных числах пользователей |
| 3.3 | Длинный (tidy) формат + rolling retention — для BI-инструментов |
| 3.4 | Средняя кривая удержания по всем когортам |

Когорта — месяц первой активности пользователя (First Touch). Как читать
результат запроса 3.1:

- **строка** — когорта, **столбец** — «возраст» когорты в месяцах;
- **M0 всегда равен 100%** по определению — это контрольный столбец: любое
  значение, отличное от 100, означает ошибку в логике запроса;
- **таблица треугольная**: у молодых когорт поздние месяцы жизни ещё не наступили,
  там `NULL` — и это принципиально не то же самое, что ноль (ноль означал бы, что
  все пользователи ушли, `NULL` — что данных пока нет).

> **Почему разница месяцев считается через `EXTRACT`, а не вычитанием дат.**
> Прямое вычитание дало бы интервал в днях, который из-за разной длины месяцев
> не переводится в номер месяца однозначно. Формула
> `(год₂ − год₁) × 12 + (месяц₂ − месяц₁)` даёт корректный номер всегда.

В запросе 3.4 среднее удержание считается **взвешенно** (сумма вернувшихся /
сумма размеров когорт), а не как среднее из процентов: иначе когорта из 50
человек получила бы тот же вес, что когорта из 5000.

## Как запустить

### Вариант 1: на реальных данных Kaggle

```bash
git clone https://github.com/<your-username>/<repo-name>.git
cd <repo-name>

# 1. Скачать датасет с Kaggle и положить CSV как data/events.csv
#    https://www.kaggle.com/datasets/mkechinov/ecommerce-events-history-in-electronics-store

# 2. Поднять Postgres
docker compose up -d

# 3. Загрузить данные и создать индексы
docker compose exec db psql -U postgres -d ecom -f /sql/01_setup_and_load.sql

# 4. Запустить аналитику
docker compose exec db psql -U postgres -d ecom -f /sql/02_activity_metrics.sql
docker compose exec db psql -U postgres -d ecom -f /sql/03_funnel_analysis.sql
docker compose exec db psql -U postgres -d ecom -f /sql/04_cohort_retention.sql
```

### Вариант 2: на синтетических данных (без регистрации на Kaggle)

```bash
python scripts/generate_sample_data.py --events 200000 --out data/events.csv
docker compose up -d
docker compose exec db psql -U postgres -d ecom -f /sql/01_setup_and_load.sql
```

Генератор создаёт данные в точно такой же схеме, с реалистичной воронкой,
недельной сезонностью и затухающим удержанием на горизонте 8 месяцев — этого
достаточно, чтобы все запросы отработали и вернули осмысленный результат.

### Интерактивная работа

```bash
docker compose exec db psql -U postgres -d ecom
```

## Что демонстрирует проект

- Работу с сырыми событийными логами, а не с готовыми витринами
- Многоуровневые CTE и оконные функции для задач, которые нельзя решить простой агрегацией
- Корректную реализацию последовательной воронки с учётом хронологии событий
- Когортный анализ с пивотированием через `CASE WHEN` и понимание разницы между
  classic и rolling retention
- Внимание к методологическим ловушкам: `NULL` vs `0` в треугольной матрице,
  взвешенное усреднение когорт, зависимость `DATE_TRUNC` от часового пояса сессии
- Продуманное индексирование под конкретные запросы, включая частичный индекс
- Воспроизводимое окружение и тестовые данные, позволяющие проверить работу
  проекта без внешних зависимостей
